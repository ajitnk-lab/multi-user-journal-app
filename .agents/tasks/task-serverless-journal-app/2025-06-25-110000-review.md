# Serverless multi-user journal with JWT auth, DynamoDB storage, and CDK infra

This change implements a complete serverless journal application: three Lambda handlers (auth, entries, search) backed by DynamoDB, a CDK v2 stack wiring API Gateway to those handlers, a single-page HTML/JS frontend, and a test suite covering all handlers. JWT-based auth with bcrypt password hashing, ULID-keyed entries for time-sorting, and in-memory content filtering for search.

**Watch for:** REST API vs HTTP API event format mismatch means deployed handlers will never route correctly — the entire API returns 400 (confirmed). Registration race condition allows exceeding the 10-user cap (confirmed). JWT secret stored as plaintext SSM `String` and embedded in the CloudFormation template (confirmed). Search and listing endpoints silently drop entries beyond the 1 MB DynamoDB page boundary (confirmed).

## High-level view

The CDK stack deploys a REST API (`apigw.RestApi`), but the handler code routes on `event["routeKey"]` — an HTTP API (v2) event format field that doesn't exist in REST API proxy integration events. This is a deploy-breaking mismatch: the handlers will fall through to `{"error": "Invalid route"}` on every request. The tests don't catch this because they construct events with `routeKey` directly.

The registration flow has a TOCTOU gap: user count check and username existence check are separate from the `put_item`, so concurrent registrations can exceed the 10-user cap or silently overwrite an existing user's password hash.

The JWT signing secret is created via `ssm.StringParameter` (plaintext, not KMS-encrypted) and baked into the synthesized CloudFormation template. Anyone with read access to the template artifact or the SSM parameter can forge tokens.

DynamoDB queries in both search and entry listing don't handle `LastEvaluatedKey`. Past 1 MB of results, older entries are silently dropped with no error signal.

1. **REST/HTTP API event format mismatch** — Handlers route on `event["routeKey"]` (HTTP API v2 format) but the CDK stack creates a REST API whose proxy events use `httpMethod`/`resource`. 2. **Registration race on user count** — The scan-then-put pattern has no conditional guard; concurrent requests can exceed the 10-user limit. Use a DynamoDB atomic counter or transact-write.
3. **Registration race on username uniqueness** — `get_item` followed by `put_item` is not atomic. Use `ConditionExpression="attribute_not_exists(username)"` on the put.
4. **JWT secret stored as plaintext** — `ssm.StringParameter` stores the secret unencrypted and embeds it in the CloudFormation template. Switch to `SecureString` (custom resource or out-of-band creation) and exclude from template output.
5. **Search loads all entries without pagination** — No `LastEvaluatedKey` handling; entries past the 1 MB boundary are silently dropped.
6. **Entry listing has the same pagination gap** — `_list_entries` also makes a single unpaginated query.
7. **JWT secret rotation not possible** — Secret generated once at deploy time, cached indefinitely in Lambda with no TTL. Redeployment invalidates all tokens instantly.
8. **Hardcoded table names in CDK** — `table_name="journal_users"` prevents deploying multiple stacks in the same account/region.

## REST API vs HTTP API event format

The CDK stack uses `apigw.RestApi`, but the handler code routes on `event["routeKey"]` — a field that only exists in HTTP API (v2) proxy integration events. REST API proxy integrations provide `event["httpMethod"]` and `event["resource"]` instead.

```
REST API event:   event["httpMethod"] = "POST", event["resource"] = "/auth/register"
HTTP API event:   event["routeKey"] = "POST /auth/register"
```

The deployed handlers will never match any route and will always return `{"error": "Invalid route"}`. The tests mask this because they manually construct events with `routeKey`. Either switch the CDK stack to `HttpApi` (which produces v2 events) or rewrite the handler routing to use `httpMethod`/`resource`.

## Registration TOCTOU and data integrity

The registration handler performs three sequential operations: scan for user count, get-item for username existence, then put-item. Two simultaneous registration requests for different usernames can both see count = 9 and both succeed, resulting in 11 users. Two requests for the same username can both see "not found" and both write, with the second silently overwriting the first user's password hash.

The fix for username uniqueness is straightforward:

```python
# Current (race-prone):
table.put_item(Item={...})

# Fixed (atomic uniqueness check):
table.put_item(
    Item={...},
    ConditionExpression="attribute_not_exists(username)"
)
```

The user-count cap is harder to enforce atomically without a separate counter item or a transactional write.

## JWT secret management

The CDK stack creates the secret with `ssm.StringParameter`, which stores the value as plaintext in Parameter Store. The handler retrieves it with `WithDecryption=True`, which is a no-op on non-encrypted parameters. Since this secret is the sole trust anchor for all authentication, it should use `SecureString` (KMS-encrypted at rest).

The secret is also embedded literally in the synthesized CloudFormation template (`JournalAppStack.template.json`), meaning anyone with read access to the template artifact sees the signing key. This is a deployment-time leak in CI pipelines.

## Search and listing pagination gap

```python
response = table.query(
    KeyConditionExpression=...,
    ScanIndexForward=False,
)
# No LastEvaluatedKey handling
```

DynamoDB returns at most 1 MB per query call. If a user accumulates more than ~1 MB of entries, the response includes `LastEvaluatedKey` and the handler silently ignores remaining pages. Older entries become unsearchable/unlisted without any error signal. Both `_list_entries` and `_search_entries` have this gap.

## Test coverage gaps

The tests cover registration validation, login, entry CRUD, search isolation, and token verification well. Cross-user isolation in search is explicitly tested, which is good.

Not tested: REST API event format (tests use HTTP API format, hiding the routing mismatch), DynamoDB pagination boundaries, SSM unreachability, CDK template synthesis, and the `content-type` header handling when API Gateway passes different formats.
