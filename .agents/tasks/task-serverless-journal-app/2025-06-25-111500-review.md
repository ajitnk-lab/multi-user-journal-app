# Serverless multi-user journal with JWT auth, DynamoDB storage, and CDK infra (v2)

This change implements a complete serverless journal application: three Lambda handlers (auth, entries, search) backed by DynamoDB, a CDK v2 stack wiring API Gateway REST API to those handlers, a single-page HTML/JS frontend, and a 22-test suite covering all handlers. The three critical issues from the v1 review — event format mismatch, registration race on username uniqueness, and DynamoDB pagination gaps — have all been fixed correctly.

**Watch for:** User-count cap still has a TOCTOU race on concurrent registration (likely). Lambda bundling omits `requirements.txt` dependencies from the asset (confirmed). The `scan` for user count doesn't paginate, so it could theoretically undercount — academic for 10 users but inconsistent with the pagination fix applied elsewhere (possible).

**Verdict**: APPROVED

## High-level view

The event format issue is resolved: all three handlers now route on `httpMethod` + `resource`, and the test helper `make_event` constructs events in the matching REST API proxy format.

Username uniqueness is now atomically enforced via `ConditionExpression="attribute_not_exists(username)"` on the put. The user-count check remains a non-atomic scan-then-put, but for a 10-user cap on a low-traffic app the worst case is 11 users, not data corruption.

Both `_list_entries` and `_search_entries` now loop on `LastEvaluatedKey`, correctly paginating through all DynamoDB results before filtering or returning.

The CDK stack bundles Lambda code from `src/` but doesn't install `requirements.txt` into that directory. Deployment will fail at runtime unless a pre-deploy step bundles dependencies into the asset. The README documents this step, so it's an operational concern, not a code bug.

## Registration user-count race

The user-count enforcement is still scan → check → put with no conditional guard on count. Two requests arriving simultaneously could both read count = 9 and both succeed, yielding 11 users. Fixing it atomically would require a counter item with `ADD` and a transactional write, which adds complexity disproportionate to the risk for a 10-user app.

## Lambda asset bundling gap

```python
lambda_code_path = os.path.join(os.path.dirname(__file__), "..", "src")
# ...
code=_lambda.Code.from_asset(lambda_code_path),
```

This bundles the `src/` directory as-is. The runtime dependencies (`bcrypt`, `pyjwt`, `python-ulid`) are not installed into the asset. If someone runs `cdk deploy` without the manual `pip install -t src/` step, all Lambda invocations will fail with `ModuleNotFoundError`. This could be addressed with CDK's `bundling` parameter on `Code.from_asset` to run pip inside a Docker container at synth time.

## Test coverage gaps

Not tested: the `ConditionalCheckFailedException` path for duplicate username registration (tests never register the same username twice to exercise that catch block), pagination behavior with multi-page DynamoDB responses, and the `_DecimalEncoder` with actual Decimal values from DynamoDB (moto returns Python ints/strings directly in most cases).
